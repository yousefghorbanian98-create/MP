# بررسی کلید قدیمی Android و استثنای محدود اسکن

این بررسی برای پاسخ به درخواست مالک انجام شد. در مرحلهٔ نخست هیچ سیاستی تغییر نکرد؛ سپس مالک با کنارگذاشتن کلید قدیمی و استثنای دو یافتهٔ دقیق موافقت کرد. دو fingerprint در `.gitleaksignore` افزوده شدند. در زمان ثبت نتایج آزمایش زیر هیچ تغییر در refs، secrets یا GitHub انجام نشده بود؛ وضعیت checkpoint و CI باید جداگانه بر اساس SHA واقعی بررسی شود. QF-00 و انتشار آغاز نشده‌اند.

## نتیجهٔ بررسی کلید قدیمی

- مخزن عمومی است. فایل keystore قدیمی و فایل properties هم‌زمان در commit `c6f29449e8a55e0ed1204847357313ca0dd7a9cb` موجود بودند. در این بررسی هر دو فایل بدون احراز هویت از GitHub دریافت و تطابق آن‌ها با blobهای همان commit فقط با هش در حافظه تأیید شد. این **امکان دسترسی عمومی** را ثابت می‌کند، نه اینکه فرد دیگری آن‌ها را دیده یا استفاده کرده باشد.
- با استفاده از داده‌های همان فایل تاریخی، آزمایش فقط metadata نشان داد که PKCS12 با رمز تاریخی باز می‌شود و دارای یک encrypted private-key bag و certificate bag است. رمزها و محتویات کلید چاپ، ثبت یا وارد این گزارش نشدند. دو یافتهٔ واقعی اسکن به فیلدهای `storePassword` خط ۲ و `keyPassword` خط ۴ در همان فایل مربوط‌اند.
- این دو فایل در درخت فعلی SHA `8e72de9b5e450b38cb3871f7d5f4383595dbdd1b` روی شاخهٔ فعال وجود ندارند؛ حذف از درخت فعلی به معنی حذف از تاریخچه یا GitHub نیست. GitHub API نشان داد commit در تاریخچهٔ دو شاخهٔ دیگر و tagهای `v0.2.0-client2` و `v0.2.0-client3` نیز قابل دسترسی است. این ارزیابی همهٔ cloneها، cacheها و سایر خدمات را پوشش نمی‌دهد.
- اثرانگشت **گواهی عمومی** کلید قدیمی، نه خود کلید یا رمز:
  `2C:33:0D:DA:8B:FE:65:FE:40:8D:A3:57:B4:E7:DD:05:15:C1:D6:AE:03:60:61:AC:28:C8:EA:65:3A:06:94:B0`
- مالک اعلام کرده برنامه هنوز نصب یا منتشر نشده و کلید قدیمی اهمیتی ندارد. باید تأیید شود که هیچ سرویس، APK نصب‌شده یا کاربرد دیگری به آن وابسته نیست و رمز تاریخی جای دیگری استفاده نشده است. کلید خودامضای Android لزوماً مکانیزم ابطال مرکزی ندارد؛ منظور از بازنشستگی، توقف همهٔ استفاده‌ها و عدم اعتماد به آن است. از کلید جدیدی که مالک قبلاً روی Windows ساخته، تا زمانی که در محیط امن تولید و نگهداری شده باشد، می‌توان پس از مقایسهٔ اثرانگشت گواهی عمومی و تست مستقل استفاده کرد؛ جدید بودن را از راه دور اثبات نکرده‌ایم.

## یافته‌ها و آزمایش استثنای فرضی

در مخزن bare موقت و جدا از workspace، تاریخچهٔ SHA شاخهٔ فعال و پنج tag با Gitleaks 8.30.1 اسکن شدند. باینری با SHA-256 مستقل منتشرشده برای باینری release تطبیق داده شد؛ دانلود asset رسمی در این محیط قبلاً ناموفق بود. محتوای گزارش scanner فقط redacted نگهداری شد و مقادیر secret نمایش داده نشدند.

با `.gitleaksignore` همان SHA شاخهٔ remote، دقیقاً دو یافته باقی ماندند؛ با تنظیم فرضی شامل فقط دو fingerprint زیر، روی همین مجموعهٔ محدود یافته صفر و exit 0 شد:

```text
c6f29449e8a55e0ed1204847357313ca0dd7a9cb:mp-app/client/android/keystore/keystore.properties:generic-api-key:2
c6f29449e8a55e0ed1204847357313ca0dd7a9cb:mp-app/client/android/keystore/keystore.properties:generic-api-key:4
```

بدون هیچ ignore و با نادیده‌گرفتن inline allow، سه یافته دیده شد: همین دو رمز و یک JWT ساختگی از تست قبلاً مستندشده. سپس یک credential کاملاً ساختگی در همان مسیر و خط ۲، ولی در commit ساختگی جدید در ref موقت غیرشاخه‌ای، اضافه شد: با همان استثناهای فرضی همچنان شناسایی و scan با exit 1 متوقف شد. این آزمون نشان می‌دهد **این مورد مشخص** به‌طور سراسری بر اساس مسیر، خط یا rule مجاز نشده؛ به‌تنهایی تضمین کشف همهٔ secretهای آینده نیست. اسکن binary keystore، همهٔ refs و همهٔ انواع اطلاعات حساس را پوشش کامل نمی‌دهد.

نتیجهٔ تست موقت، **CI سبز روی GitHub یا بازبینی مستقل نیست**. سابقهٔ CI واقعی `44391354746` روی SHA فوق، secret-scan ناموفق با همان دو یافته داشت. تاریخچهٔ کامل همهٔ شاخه‌های دیگر در این تست اسکن نشده است.

## تصمیم لازم و اقدامات بعدی

1. مالک با کنارگذاشتن و بی‌استفاده‌بودن کلید و رمزهای قدیمی موافقت کرد؛ دو یافته به‌عنوان «واقعی اما متعلق به اعتبارنامهٔ بازنشسته» ثبت شدند، نه false positive. استفاده‌نشدن در سرویس‌های دیگر و متفاوت‌بودن گواهی کلید جدید از راه دور مستقلاً تأیید نشده‌اند؛ تا تأیید کلید جدید، امضای انتشار PASS نیست.
2. **مسیر کم‌تغییر انتخاب‌شده:** مالک استثنا را به‌جای الزام قبلی حذف دو مورد واقعی از تاریخچه تصویب کرد. صرفاً همان دو fingerprint با توضیح، محلی به `.gitleaksignore` اضافه و regression مثبت/منفی در `scripts/test_retired_signing_scan.py` با Gitleaks واقعی 8.30.1 اجرا شد. هر دو حالت شناسایی دادهٔ ساختگی، استثنای دقیق و شناسایی دوبارهٔ secret جدید موفق بودند. اجرای همین تست به job اسکن در workflow محلی اضافه شد. اسکن مجدد تاریخچهٔ شاخهٔ remote و پنج tag با policy محلی exit 0 و صفر یافته داد؛ این نه اسکن کل refs دیگر و نه CI واقعی است. بررسی مستقل و CI روی SHA commit/pushشده هنوز انجام نشده‌اند. هیچ global allowlist، استثنای نام مسیر، rule سراسری یا خاموش‌کردن scan مجاز نیست. دادهٔ تاریخی همچنان عمومی باقی می‌ماند.
3. **مسیر پاک‌سازی بیشتر:** حذف فایل‌ها از همهٔ refs مرتبط نیازمند برنامهٔ هماهنگ با مالک refs، بازبینی و احتمالاً بازنویسی تاریخچه است. این کار SHAها را تغییر می‌دهد و کپی‌های دیگر یا cacheها را الزاماً از بین نمی‌برد؛ پشتیبانی GitHub محدودیت‌های خود را دارد. بدون مجوز و فرآیند مناسب روی شاخه‌های دیگر یا refs مشترک اقدامی نمی‌شود. کنارگذاشتن کلید حتی در صورت پاک‌سازی ضروری است.
4. وضعیت واقعی secrets/variables ‏Actions قابل تأیید نیست (API برای این اتصال 403). پیش از امضای انتشار، مالک باید اطلاعات کلید جدید را امن در GitHub Actions تنظیم کند و اثرانگشت گواهی عمومی آن را با `MP_ANDROID_CERT_SHA256` مطابقت دهد؛ secretها در چت یا Git ثبت نشوند. build و verify روی SHA واقعی باید جداگانه موفق شوند.

موضوع کلید تنها مانع checkpoint نیست: هنگام این بررسی شاخهٔ remote جلوتر و worktree دارای تغییرات حفظ‌شدنی بود؛ QA مستقل و میزبان واقعی زیراجنت هنوز اثبات نشده‌اند. وضعیت ذخیرهٔ اسناد و CI باید برای SHA مربوطه جداگانه بررسی شود.
