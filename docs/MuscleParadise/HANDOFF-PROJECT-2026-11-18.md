## ۱. هشدار حیاتی پیش از شروع نشست جدید

این سند و برخی اسناد مرتبط در زمان تهیه **تغییر محلی و/یا untracked** هستند؛ موجود بودن آن‌ها در workspace به معنی موجود بودنشان در GitHub یا clone جدید نیست. فایل‌های ignored، home و ابزارهای نصب‌شده نیز بین sandboxها تضمین بقا ندارند. قبل از بستن نشست فعلی، نسخهٔ پشتیبان امن یا checkpoint تأییدشده از تغییرات لازم داشته باش؛ secret، فایل امضا، تنظیمات محلی حساس، دادهٔ واقعی و cache ابزار را همراه اسناد عمومی منتشر نکن. قابلیت‌های محیط Arena برای حفظ workspace/انتقال بین نشست‌ها را بررسی کن؛ رفتار رابط و نام دکمه‌ها ممکن است تغییر کند و در این سند تضمین نشده است.

در آخرین بررسی:

- repository عمومی است اما مجوز آن [اختصاصی](../../LICENSE) است؛ شاخهٔ این نشست `arena/b0e55b62-mp` و HEAD محلی `5482930587ce18e14f136d78296542a2de5af091` بود.
- سرِ همان شاخه در GitHub روی `8e72de9b5e450b38cb3871f7d5f4383595dbdd1b` بود؛ نسبت به HEAD محلی ۸ commit جلوتر. fetch فقط برای خواندن انجام شد؛ **pull، reset، ادغام، push یا force push برای رفع اختلاف انجام نشد**.
- workspace دارای تغییرهای پیشین و untracked است. از ۲۶ فایل متفاوت بین دو commit، در زمان بررسی ۲۴ فایل محلی byte-identical با سر remote و دو فایل `.finn/state/LEDGER.md` و `.finn/state/STATE.md` دارای تغییرات محلی افزوده بودند. یک `git read-tree -n -m -u HEAD FETCH_HEAD` فقط dry-run، به علت تغییر ledger با exit 128 مانع fast-forward را گزارش کرد؛ بنابراین هیچ تغییر فایل یا ref صورت نگرفت. این شمارش snapshot است و باید در نشست تازه دوباره بررسی شود.
- قبل از انتشار، شاخه باید با روش **غیرمخرب و بازبینی‌شده** همگام شود، بدون از دست رفتن تغییرهای محلی، بدون `git pull`، `reset`، `clean` یا `force push`. این مسئله را با تغییر نام شاخه یا ساخت شاخهٔ دیگر دور نزن. تنها اجازهٔ صریح و فعلی برای شاخهٔ همان نشست معتبر است. اگر راه غیرمخرب در اختیار نیست، مسدود ثبت کن و از مالک/پشتیبانی مسیر امن انتقال workspace را بخواه.
- [`settings.local.json`](../../.claude/) ممکن است تنظیم شخصی داشته باشد؛ به‌طور پیش‌فرض stage/publish نشود. فایل‌های پیشین را حذف، overwrite یا stage انبوه نکن. هیچ secret/کلید/پسورد را چاپ یا در چت درخواست نکن.

## ۳. هدف محصول و تصمیم‌های مالک

**محصول:** سامانهٔ فارسی‌محور باشگاه با Android عضو، وب کادر و FastAPI؛ زیر ۱۰۰ عضو در آغاز برآورد شده، همزمانی واقعی نامعلوم. همهٔ قابلیت‌های اصلی باید برای انتشار اول آماده و آزموده شوند: ثبت‌نام/عضویت، تمرین و کلاس، تغذیه، ارزیابی، حضور QR، چت و فروشگاه. برنامه عمدتاً آنلاین است؛ عمل وابسته به سرور نباید در قطع ارتباط موفق اعلام شود. اپ اختصاصی کادر و نصب دسکتاپ الزام انتشار اول نیستند.

**نقش و امنیت:** فقط `super_admin` هر نقش مجاز را اعطا یا سلب می‌کند؛ ساخت super_admin دوم از API عادی ممنوع باقی بماند. برای هر admin مجوزهای شخصی on/off و زمان‌دار، تفکیک read/write و enforce سروری لازم است. نقش‌های دیگر حقوق ثابت دارند؛ اختیار فیش برای نقش غیر admin را بدون تصمیم جدید فرض نکن. مالی برای admin و manager پیش‌فرض خاموش است؛ super_admin مجاز است. آزمون مالکیت، لغو فوری، انقضا، دو admin، مسیرهای جایگزین و audit ضروری است.

**پرداخت:** در انتشار اول فقط کارت‌به‌کارت با فیش خصوصی و تطبیق انسانی مستقل از بانک توسط super_admin یا admin مجاز؛ فیش به‌تنهایی اثبات واریز نیست. تأیید، ثبت مالی، فعال‌سازی خودکار اشتراک و رویداد اعلان باید تراکنشی و idempotent باشند. `card` قدیمی کارت‌خوان است و نباید با `card_to_card` یکی شود. حداقل policy مجزای M113 نوشته شده، اما workflow کامل هنوز اثبات نشده است.

**مالی و تحلیل:** ثبت هزینه‌های بیرونی، ریز و جمع تراکنش، گزارش هفتگی/ماهانه/سالانه شمسی، export امن و کنترل دسترسی. تمایز دریافت نقدی، درآمد و نتیجهٔ عملیاتی، عدم دوباره‌شماری wallet و refund و تعریف با حسابدار ضروری است. تخمین‌های دریافت/جریان پول، تمدید و نتیجهٔ عملیاتی فقط با دادهٔ کافی، backtest و بازهٔ عدم قطعیت؛ وگرنه «نامشخص». `due_rial=0` فعلی را بدهی واقعی معرفی نکن.

**اعلان:** صندوق داخلی عضو و push عضو و مالک، اعلان گزارش به مالک، تحویل و رفتار دستگاه بدون GMS در محیط هدف بررسی شود. push جای inbox پایدار را نمی‌گیرد. n8n برای منطق و اعلان محصول طبق [ADR-005](adr/005-n8n-boundary.md) مجاز نیست مگر تصمیم جدید.

**داده و انتشار:** عکس پیشرفت بدن خارج از scope است، نه عکس فیش یا محصول؛ قبل از حذف هر دادهٔ احتمالی inventory و مجوز لازم است. دادهٔ سلامت/ارزیابی به اطلاع‌رسانی، مبنای مجاز، دسترسی محدود، retention و بررسی حقوقی نیاز دارد. staging ترجیحاً ابری ایرانی با دادهٔ ساختگی و اجازهٔ جدا؛ بودجه نامعلوم است. استفادهٔ واقعی یک‌باره برای همهٔ باشگاه پس از تکمیل همهٔ گیت‌ها و تأیید مالک؛ پایلوت محدود واقعی تصمیم فعلی نیست. خرید، deploy، release، پرداخت واقعی و دادهٔ واقعی بدون مجوز خاص ممنوع.

## ۵. FINN، REA، ECC و Repowise

- **FINN:** Forge → Inspect → Normalize → Next، با واحد `QA-QF-n` برای هر برش شامل همهٔ دکمه‌ها و خروجی‌های حوزه، اتصال واقعی UI/API/DB، نقش/امنیت، عدم تداخل، خطا/بار، تست و مستندات. گیت نهایی جای QA هر حلقه را نمی‌گیرد. مالک checkpoint GitHub پس از هر loop را خواسته: تا ثبت امن و بررسی remote، توسعهٔ loop بعدی آغاز نشود. پس از رفع مانع ماندگاری، loop آماده بدون نظارت روتین ادامه یابد؛ در دیگر موانع واقعی، تنها وابسته‌ها مسدود و مستقل‌ها ادامه یابند. [طرح تفصیلی و گیت checkpoint](PLAN-FINN-ECC-MICROLOOPS-QA.md) · [پیشنهاد زیراجنت‌ها، منتظر تأیید](PROPOSAL-SUBAGENTS-AND-CHECKPOINTS.md).
- **REA:** [گزارش REA](REPORT-REA-ECC-SUBAGENTS.md) فقط inventory پالایش‌شده و تحلیل static محدود را نشان می‌دهد؛ `partial` به معنای audit کامل نیست. از اطلاعات محرمانه در خروجی پرهیز کن.
- **ECC:** [گزارش نصب](../../finn/reports/ecc-native-setup.md) و [آزمون ایزوله](REPORT-ECC-SUBAGENT-SMOKE.md): CLI نقش planner و ابزار Task را در آزمون بدون credential شناخت، اما مدل به خطای احراز هویت رسید و هیچ child اجرا نشد. این مشاهده تجربهٔ احتمالی موفق مالک در نشست دیگر را رد نمی‌کند. اگر میزبان جدید قابلیت واقعی دارد، با شاهد parent/child از آن استفاده کن؛ نقش‌آفرینی، فایل agent و `consult` را اجرای مستقل اعلام نکن. [سنجش جایگزین‌های رایگان](REPORT-FREE-ECC-ALTERNATIVES-2026-11-18.md) نشان داد ترکیب Superpowers، Agency و OpenCode می‌تواند با پاسخ اسکریپت‌شدهٔ غیرهوشمند skill را بخواند و child session بسازد؛ آزمون AI واقعی و برتری بر ECC باز است و هیچ جایگزینی مصوب/نصب‌شده روی پروژه وجود ندارد.
- **Repowise:** ایندکس `.repowise/` و محیط محلی ابزار ignored/موقتی هستند و در sandbox جدید تضمین بقا ندارند. در محیط این نشست binary، بستهٔ Python و پوشهٔ index موجود نبودند؛ index به‌روزرسانی نشده است. `DX-REP-01` در TODO قبلی برنامه‌ریزی شده، MCP مستقیم در بررسی پیشین Arena دیده نشده. در صورت دسترسی، ابتدا status و version و اثر تغییر/داده را بررسی و فقط در صورت نیاز و با حفاظت داده، index بدون مدل را بازسازی کن؛ فایل Git-tracked جایگزین آن نیست و بالعکس. مسیر navigation و diagramها در [docs hub](../README.md) به‌روز شده‌اند.
- بازبینی wheel نسخهٔ `repowise 0.61.0` نشان داد `init --yes` به‌تنهایی ممکن است اتصال editor و hook بسازد و provider انتخاب کند؛ بی‌بررسی و کورکورانه اجرا نشود. تنظیمات مستقلِ `--no-prose`, `--no-editor-setup`, `--no-hook`, `--no-distill-hook`, `--no-agents`, `--no-claude-md`, `--no-save-key` و excludeهای دقیق را در محیط ایزوله و بدون credential قبل از هر بازسازی ارزیابی کن. خروجی یا ایندکس ممکن است حساس باشد؛ گیت secret-scan فعلی شکست دارد، پس بدون ارزیابی دایرهٔ فایل/تاریخچه index عمومی منتشر نشود. wheel فقط برای بازرسی در مسیر موقت دانلود شد؛ نصب، init، اتصال MCP و اجرای مدل انجام نشد.

## ۶. تحقیق منابع و ورود کد خارجی

نامزدهای مهم: uploadshield برای بخشی از کنترل آپلود، persiantools برای تبدیل شمسی، ledgerline برای مطالعهٔ تراکنش/ledger، StatsForecast برای backtest و مدل آماری، pgBackRest برای بکاپ PostgreSQL و SDK اعلان مشروط به سرویس. هیچ‌کدام در این طرح پذیرفته یا به runtime اضافه نشده‌اند. ledgerline در بررسی موجود IRR و auth نداشت؛ pgdispatch webhook/async/PostgreSQL است، نه راه‌حل مستقیم push. هر مورد نیازمند URL و نسخهٔ دقیق، مجوز کد/دارایی/داده/weights/وابستگی‌ها، notice، امنیت، سازگاری و آزمون است. GPL/AGPL یا مجوز نامعلوم و سرویس خارجی را بدون ارزیابی حقوقی/اجازه به محصول اختصاصی وارد نکن. [جزئیات و شواهد](OSS-DEEP-RESEARCH-2026-11-18.md).

## ۷. دستور کار برای عامل بعدی

1. ابتدا پیام شعبهٔ **همان نشست جدید** و وضعیت شاخه/محیط را بخوان؛ وضعیت Git، HEAD، فایل‌های dirty و untracked، سلامت ابزار، docs hub و این هندآف را بررسی کن. branch قدیمی را از متن این سند به‌زور checkout نکن و دستورهای قدیمی reset/checkout در handoff تاریخی را اجرا نکن.
2. اختلاف محلی/remote و وجود همهٔ فایل‌های مرتبط را بدون دستکاری بررسی کن. اگر فقط clone GitHub موجود است، فایل‌های untracked این نشست را موجود فرض نکن. اگر continuity نامعلوم است، قبل از تغییر داده یا merge وضعیت را `BLOCKED` ثبت و مسیر انتقال امن را هماهنگ کن.
3. قصد کاربر را بخوان: درخواست کنونی به‌روزرسانی مستندات و انتقال است. **ساخت محصول هنوز با این کار شروع نشده**؛ پس از دستور شروع ساخت، از `QF-00` شروع کن و per-loop QA را تکرار کن. مبنای برنامه و تصمیم‌های جدید بر ادعاهای قدیمی ناسازگار مقدم‌اند.
4. در هر loop ماتریس عمل/خروجی و role، منبع M/C/R/N/A، تست شکست، wiring، security، failure/load، رگرسیون، سازگاری و نتیجهٔ واقعی را ثبت کن. دادهٔ ساختگی و کمترین دسترسی؛ رفع موارد مستقل بدون توقف روتین. فایل‌های قبلی را بی‌دلیل حذف/overwrite نکن؛ حذف کد مرده فقط با اثبات نبود مصرف و تست، نه پاک‌سازی فراگیر.
5. در پایان هر بخش، ارتباط با بخش‌های قبلی را رگرسیون کن. در تغییرات بعدی بخش آسیب‌دیده را بازآزمون کن؛ full-suite/CI و دستگاه در گیت‌های مربوط و روی همان نسخه لازم‌اند. ادعای «کلاس جهانی» به معنی تضمین بی‌نقص‌بودن نیست.
6. مستندات، معماری و notice را همراه تغییر به‌روز کن؛ `python3 scripts/docs_gate.py`، لینک‌های سندهای جدید و آزمون‌های دامنه را اجرا کن؛ handoff را با قدم بعدی و شواهد به‌روز نگه دار. هر permission برای push/deploy/secret/history طبق درخواست همان زمان محدود است.

## ۸. موارد نیازمند تصمیم یا دسترسی بیرونی

- بودجه، میزبان/دامنه، پشتیبانی، RPO/RTO و ساعت گزارش؛ قبل از خرید یا استقرار تأیید بگیر.
- روش تأیید امن بانکی، ادمین‌های مجاز، تعریف حسابداری و نتیجهٔ عملیاتی/مالیات با مسئول مربوط.
- سیاست اطلاع‌رسانی، مبنای قانونی و retention برای سلامت، چت، فیش و backup؛ متخصص حقوقی و مالک تأیید کنند.
- انتخاب سرویس push و رفتار دستگاه/شبکهٔ ایران و fallback؛ بدون تضمین تحویل.
- رفع secretهای قدیمی و دسترسی CI؛ امضای Android با کلید پایدار، بدون فرستادن مقادیر محرمانه در گفتگو.
- اگر مدل/میزبان خارجی برای ECC استفاده می‌شود، provider، هزینه، محدودهٔ داده و مجوز ارسال کد باید از قبل روشن باشد. برای نمونهٔ تاریخی نشست دیگر تنها شاهد غیرمحرمانه مفید است.

## ۹. روش امن بازکردن نشست جدید در Arena

1. **فعلاً نشست فعلی را پاک یا کنار نگذار.** تا زمانی که checkpoint شامل همهٔ فایل‌های لازم و قابل انتقال با روش امن تأیید نشده، clone تازه ممکن است کارهای محلی/untracked را نداشته باشد. دفع خطر اختلاف هشت commit را از تیم/ابزار پشتیبانی یا عامل با مجوز مناسب و روش غیرمخرب پیگیری کن.
2. در Arena یک گفت‌وگوی Agent Mode جدید برای همین repository باز کن؛ اگر رابط اجازه می‌دهد همان workspace/شاخهٔ مورد نظر را انتخاب کن. اگر سامانه شاخهٔ جدید تعیین کرد، پیام branch جدید و محدودیت‌هایش ملاک‌اند؛ خودت نام branch را به عامل تحمیل نکن و از او نخواه به branch دیگری سوئیچ کند.
3. در نشست جدید بپرس آیا `docs/MuscleParadise/HANDOFF-PROJECT-2026-11-18.md` و [طرح QF](PLAN-FINN-ECC-MICROLOOPS-QA.md) واقعاً موجودند و آیا تغییرات محلی قبلی در همان workspace حاضرند. اگر نیستند، **ادامهٔ ساخت نده**؛ از checkpoint تأییدشده بازیابی یا مسیر انتقال امن را هماهنگ کن. صرف لینک GitHub تا پیش از انتشار واقعی کافی نیست.
4. متن §۱۰ را در نشست جدید بفرست. برای شروع ساخت، جملهٔ مجوز شروع را فقط وقتی واقعاً می‌خواهی اضافه کن؛ انتشار یا استقرار را همچنان جداگانه کنترل کن.
5. عامل باید branch/HEAD و ابزار را راستی‌آزمایی و بدون چاپ secret گزارش کند، بعد به ترتیب QF جلو برود. نشست جدید لزوماً فرآیند قبلی یا subagentهای آن را زنده نگه نمی‌دارد؛ نتایج و موانع باید در فایل‌ها ثبت شده باشند.
