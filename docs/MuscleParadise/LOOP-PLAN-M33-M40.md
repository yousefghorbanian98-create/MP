## ۰) یادآوری فرایند ثابت هر میکرو-لوپ (کپی از لوپ سوم — بدون تغییر)

`spec (ردیف نیازمندی + شاهد + حدود) → build (اول موجود، E12 برای هر OSS) → gates (تست/ایستا) → S3b بازبینی خروجی‌ها (OUTPUT-AUDIT) → S3c دود بار (Locust در endpoint جدید) → S4 design → S5 security → S6 science (داده←قاعده←شاهد←تصمیم) → S7 rights → S8 e2e → S9 گزارش+push`

**گیت‌های ۹گانهٔ پایان هر چرخه (بدون تغییر):** build سبز · پوشش ≥۷۰٪ بدون کاهش · lint صفرخطا · bandit+pip-audit بدون بحرانی جدید · گزارش code-reviewer بدون Blocker · رگریشن‌ها سبز · مستندات+CHANGELOG به‌روز · LEDGER بدون درس تکراری · یک commit با پیام `mp(Mxx): … [finn]`.

**افزودهٔ این لوپ (از سند شدنی):** برای هر محور/قاعده/نُرم ورودی، ردیف `rule-evidence` (الگوی `templates/rule-evidence.template.json` بستهٔ کاربر) ثبت شود — «مصدر/نسخه/حقوق/دامنه/تأیید».

## ۳) قواعد اجرایی (تکراری از لوپ سوم — پابرجا)

1. **S3b اجباری:** هر دکمه/فرم/مسیر جدید ← خروجی ملموس + ثبت در `OUTPUT-AUDIT` + تست دودی در گزارش.
2. **S3c اجباری برای endpoint جدید:** Locust کوتاه (۱۰ کاربر/۱۰s) — «کرش زیر بار» ممنوع.
3. **هیچ‌چیز «تست‌نشده» = «پیاده‌شده» نیست** (Handoff).
4. هر میکرو = commit + push (یک‌بار rebase در صورت رد push).
5. دادهٔ واقعی هرگز در Git/تست/لاگ/REA (G6/E09).
6. هر ورودی OSS/داده ← ثبت E12/NOTICE قبل از ادغام.
7. جدول توانایی/شاهد/شکاف در آغاز هر گزارش milestone (Handoff).

## ۴) تصمیم ECC (پاسخ پرسش کاربر — ۲۴ آبان ۱۴۰۵)

**توصیه: بله — ادامه تحت ایجنت‌های ECC، با یک تنظیم چابک.**
- **چرا بله:** پروژهٔ ۱۴توانایی، علمی/شواهدمحور است؛ ECC-3 (استناد/نُرم/بدون ضریب از حافظه) و ECC-4 (حقوق منابع/آزمون‌های تجاری/ادعای بالینی) دقیقاً همان چیزی‌اند که در غیر این صورت در دفاع پایان‌نامه گم می‌شود. سابقهٔ لوپ سوم: این ایجنت‌ها نقص‌های واقعی گرفتند.
- **تنظیم چابک:** پنج ایجنت به‌جای «پاس‌های جداگانهٔ سنگین»، در هر میکرو **هم‌زمان به‌عنوان عینک بازبینی** عمل کنند (چک‌لیست موازی)؛ گیت‌های ۹گانه سر جایشان؛ S3b/S3c اجباری (خواستهٔ صریح شما). هزینهٔ فرایند پایین می‌آید، تفکیک مسئولیت‌ها (به‌ویژه علم/حقوق) می‌ماند.
- **سطح L2** بدون تغییر؛ ارتقا فقط با تصمیم صریح شما.
