# برنامهٔ توسعهٔ جزءبه‌جزء FINN/ECC با تضمین کیفیت تکرارشونده
> **ECC حذف شد (۲۰۲۶-۱۱-۱۹).** هر دستور نصب ECC، مسیر `.claude/...` یا فراخوانی `ecc:*` در این سند **تاریخی** است و اجرا نمی‌شود. نقش‌ها/چک‌لیست‌ها فایل متنی‌اند و runtime یا API مدل لازم ندارند.



**آخرین به‌روزرسانی:** ۲۰۲۶-۱۱-۱۹ · **شاخهٔ فعال این نشست:** `arena/a72fbc61-mp` · **وضعیت جاری:** QF-00 آغاز شده؛ baseline/inventory اولیه ثبت و `api/routes.json` به inventory سطح operation ارتقا یافت (تست red→green و full backend موفق). بااین‌حال Q0–Q10 کامل نیستند و گیت QF-00 به‌علت نگاشت همهٔ interactionها/QA مستقل/checkpoint هم‌شاخه باز است. جزئیات شاهد در [گزارش QF-00](REPORT-QF-00-BASELINE-2026-11-19.md) است. متن تاریخی پایین‌تر در تاریخ ثبت خودش حفظ شده و وضعیت جاری را تعیین نمی‌کند.

**هدف:** هر برش کوچک و قابل‌آزمون، مسیر کامل Forge → Inspect → Normalize → Next را به همراه **واحد کیفیت همان برش** طی کند، سپس برش بعدی آغاز شود. نه اینکه ابتدا همهٔ کدها نوشته و آخر کار یک QA عمومی انجام شود. با حفظ [TODO محصول](TODO-CLOUD-FINANCE-ACCESS.md)، [طرح پرداخت](PLAN-MANUAL-TRANSFER.md)، [پروتکل FINN](FINN_LOOP.md) و [تحقیق منشأ](OSS-DEEP-RESEARCH-2026-11-18.md). این سند دستور حذف یا بازنویسی صف فعلی [TODO جاری](TODO-2026-11-16.md)، آثار قبلی یا داده‌ها نیست؛ شناسه‌های `QF` طرح جزئی‌سازی‌شدهٔ CF-00..CF-10 هستند، نه ادعای تکمیل آن‌ها.

**قید اجرا:** مالک آماده‌سازی تا لحظهٔ شروع loop و نهایی‌سازی [تخصیص وظایف زیراجنت‌ها](PROPOSAL-SUBAGENTS-AND-CHECKPOINTS.md) را به صلاحدید عامل واگذار کرد؛ این دستور هنوز شروع اجرای QF-00 یا ساخت محصول نیست. پس از دستور شروع، توالی آماده‌ها بدون نظارت روتین ادامه می‌یابد. checkpoint امنِ commit و push **به شاخهٔ فعلی همان نشست** پس از هر میکرولوپ جزو فرایند لازم است؛ این مجوز برای merge به main، deploy، release، خرید، انتشار اطلاعات حساس، تغییر دادهٔ واقعی، تغییر مخرب history یا فرستادن کد به سرویس مدل نیست. اختلاف فعلی شاخه و امنیت سابقه پیش از شروع باید غیرمخرب تعیین‌تکلیف شوند؛ §۲.۱ را ببین. عدم امکان ادامه در پایان turn/session را صادقانه ثبت کن؛ این سند daemon یا تضمین اجرای خودکار میان نشست‌ها نیست.

## ۱. واژه‌های منشأ: شفافیت قبل و بعد از کدنویسی

- **M — موجود در MP:** استفاده/اصلاح کد و dependency فعلی. موجود بودن به معنی درست‌بودن نیست. ابتدا `git status` و diff را بخوان، تغییرهای قبلی/untracked دیگران را حفظ کن.
- **C — نامزد مستقیم:** کتابخانه یا نمونهٔ مشخص برای *احتمال* dependency، نصب ابزار، یا اقتباس انتخابی. تاکنون در این برنامه هیچ مورد جدید پذیرفته و وارد نشده؛ همه `CANDIDATE` هستند. تصمیم نهایی تنها پس از license، نسخهٔ pin، سازگاری، امنیت، توجیه اندازه و تست؛ ممکن است رد و با کدنویسی اختصاصی جایگزین شوند.
- **R — فقط مرجع ایده/رفتار:** بدون کپی کد/دارایی/داده. GPL/AGPL یا مجوز مبهم، مدل‌های HF و دیتاست‌های تأییدنشده را طبق تحقیق قبلی اینجا قرار بده؛ کپی یا دانلود/استفاده بدون گیت حقوق و داده ممنوع است.
- **N — توسعهٔ اختصاصی توسط عامل اجراکننده:** فایل‌ها، اتصال‌ها، قواعد، migration، UI و تست‌هایی که در MP نوشته یا اصلاح می‌شوند. عامل در زمان اجرا نتیجه و diff را ثبت می‌کند، نه اکنون.
- **A — پذیرفته/واردشده:** تنها بعد از ثبت شواهد واقعی. برای هر قطعه: نوع dependency/vendored/copied/asset/data/model/service، URL، commit/tag/نسخه و SHA256 artifact، دقیقاً مسیر مبدأ و مقصد، copyright و license/notice، تغییرات، پکیج‌های انتقالی، آسیب‌پذیری و سازگاری، تست و تصمیم حقوقی. هنگام استفاده از بسته `NOTICE-THIRD-PARTY.md` و lockfileهای مناسب را حفظ/تکمیل کن؛ مجوز کد، فونت/تصویر، داده و weights جدا هستند. هر تغییر مبتنی بر source باید provenance داشته باشد؛ `R` نه مجوز کپی است و نه جزو واردشده.

**وضعیت هم‌اکنون:** A جدید برای این برنامه = **هیچ**؛ REAهای تحقیق قبل فقط inventory `partial` هستند. فهرست زیر قصد اولیه است نه قول اینکه هر نامزد پذیرفته می‌شود. دکمه‌های موجود و دامنه‌های دیگر پروژه بدون بررسی از محصول حذف نمی‌شوند. `image_picker`, Casbin, Recharts, APScheduler در manifest فعلی دیده شده‌اند؛ scanner و اعلان محلی بسته‌های پیشنهادی‌اند نه وجود اثبات‌شده در client.

## ۲. تعریف واحد QA مستقل در هر میکرولوپ

`QA-QF-n` یک **بستهٔ کار و صورت‌جلسهٔ جدا برای همان n** است، نه سازمان، agent یا فرآیندی که اکنون اجرا شده باشد. هر ردیف §۴ الزاماً همهٔ Q0–Q11 زیر را اجرا یا با دلیل دقیق `N/A` کند؛ Q2، Q3، Q4، Q5، Q8، Q10 و Q11 را برای هر تغییر محصولی نمی‌توان صرفاً به‌دلیل کوچک‌بودن حذف کرد. اگر حوزه‌ای مصداق ندارد (مثلاً endpoint یا دکمه‌ای در یک loop زیرساختی وجود ندارد)، «N/A + دلیل + دامنهٔ جست‌وجو»؛ اگر لازم ولی اجرا نشده `BLOCKED`/`UNKNOWN`، هرگز N/A. به‌روزکردن فقط تست mock جای اتصال واقعی نیست. در نبود بازبین مستقل، عامل اصلی بررسی دستی انجام می‌دهد و استقلال را `BLOCKED` می‌نویسد؛ آن را review مستقل یا ECC subagent جا نمی‌زند.

### چرخهٔ اجباری تکرارشونده

1. **Forge:** Q0–Q1 و طراحی برش n، کدنویسی اختصاصی N و ورود C فقط با گیت منشأ؛ هیچ‌کدام را از پیش واردشده قلمداد نکن.
2. **Inspect:** REA در ورودی متناسب در صورت نیاز، source/contract و مرور خط‌به‌خط؛ ECC نقش‌های §۳ در صورت اجرای واقعی یا مرور دستی صریح؛ Q2–Q5. برای فایل/سرویس بیرونی از دادهٔ ساختگی استفاده شود.
3. **Normalize:** Q6–Q9 و اصلاح تا قبولی، تست دوباره بعد از هر refactor، مستندات API/معماری/تهدید در همان diff. یافته را از شمارش خارج یا severity را کم نکن تا گیت سبز شود.
4. **Next:** Q10 و checkpoint تأییدشدهٔ GitHub طبق §۲.۱، سپس n+1. بخش کامل فقط وقتی تمام ریزبرش‌های آن و QAهای جداگانه بسته باشند. QA نهایی QF-32 جای QA هر برش را نمی‌گیرد. اگر شاهد تازه نشان دهد برش قبلی آسیب دیده، همان برش و رگرسیون‌های وابسته دوباره باز می‌شوند؛ شاهد قدیمی بدون اعتبار مجدد کافی نیست.

### ۲.۱. شرط جدید: مستندسازی و checkpoint GitHub برای هر میکرولوپ

این بند درخواست مالک برای حفظ خروجی هر حلقه در GitHub را ثبت می‌کند؛ تخصیص نقش‌ها برای آماده‌سازی پذیرفته شده، ولی شروع توسعه در این گام صادر نشده است.

1. **پیش از QF-00:** شاخه/HEAD محلی و سر شاخهٔ دوردست و وضعیت dirty/untracked را بدون pull/reset بررسی کن. با بازبینی دقیق، مسیر مجاز و غیرمخرب checkpoint و انتقال آثار قبلی را تعیین کن. اگر امکان push fast-forward بدون از دست رفتن آثار یا انتشار ناخواسته نیست، `BLOCKED` ثبت کن؛ شاخهٔ دیگری نساز و force-push نکن. در snapshot فعلی HEAD محلی `5482930` و شاخهٔ GitHub `8e72de9` با فاصلهٔ ۸ commit و فایل‌های dirty بود؛ در زمان اجرا دوباره بررسی شود.
2. **در پایان هر حلقه:** مستندات مرتبط، ماتریس Q0–Q11 و فرمان/نتیجه/skip، وضعیت مانع، منشأ و notice، فایل‌های لازم برای ادامه، شاخه و شناسهٔ commit را تکمیل کن. فایل‌های مربوط به آن حلقه و آثار قبلی لازم را به‌صورت انتخابی و با review دقیق stage کن؛ staged diff و secret scan لازم را پیش از commit بررسی کن. از stage انبوه و انتشار محتوای unrelated/ناشناخته پرهیز کن.
3. **ثبت پایدار:** پس از حصول شرایط ایمنی، commit مشخص برای آن حلقه بساز و فقط به شاخهٔ فعلی `origin`، بدون force، push کن. موفقیت دستور، SHA و تطابق سر شاخه در GitHub را بررسی و با لینک commit و نتیجهٔ CI همان SHA ثبت کن؛ CI اجرا‌نشده/ناموفق همچنان `UNKNOWN`/`FAIL` است. یک checkpoint می‌تواند نتیجهٔ واقعی `BLOCKED` یا `FAIL` را مستند کند؛ وجود commit به معنی قبولی QA یا انتشار محصول نیست. برای جلوگیری از وابستگی دوریِ SHA به محتوای همان commit، SHA را در ledger/گزارش بعدی یا شناسهٔ commit در GitHub/پیام commit ثبت کن، نه اینکه ادعا شود سند حاوی SHA خودش است.
4. **پیش از حلقهٔ بعدی:** همهٔ آثار لازم و مجاز آن حلقه در commit در دسترس باشند و push/تطابق remote تأیید شده باشد. اگر اتصال GitHub، اختلاف remote، تضاد فایل یا بررسی امنیت مانع است، checkpoint `BLOCKED` بماند و توسعهٔ حلقهٔ جدید آغاز نشود تا درخواست مالک دربارهٔ باقی‌نماندن خروجی فقط در sandbox نقض نشود؛ تعمیر بی‌خطر یا بازبینی مستقلِ بدون ایجاد آثار توسعه‌ای مجاز است. این توقف مختص گیت ماندگاری است؛ پس از رفع آن، حلقه‌های مستقل مطابق D-033 بدون تأیید روتین ادامه یابند.
5. **استثنای امنیتی:** مخزن عمومی است. secret، کلید امضا، credential، دادهٔ شخصی، عکس فیش واقعی، log خام حساس، virtualenv/cache، مدل حجیم و تنظیمات محلی حساس هرگز برای «خالی‌کردن sandbox» در GitHub عمومی قرار نگیرند. محتوای حساس لازم فقط در محل خصوصیِ تأییدشده/مدیریت secret مناسب و با ثبت اشارهٔ غیرمحرمانه؛ اگر مقصد امن موجود نیست، گزارش `BLOCKED` و هماهنگی با مالک. ابزار موقتی قابل‌بازتولید باید با نسخه و دستور و شاهد غیرحساس ثبت شود، نه الزاماً commit کردن binary/cache. هدف، ماندگاری **همهٔ آثار لازم و مجاز** است، نه انتشار بی‌قید هر فایل sandbox.
6. **مرز ادغام:** ذخیره در branch، تغییر main یا نمایش README روی صفحهٔ پیش‌فرض نیست. main/release/deploy پس از گیت‌های امنیتی، CI و تأیید لازم جداگانه بررسی می‌شوند. هیچ CI قرمز یا history آلوده به‌صرف checkpoint بی‌اهمیت فرض نشود.

### ترتیب و عدم توقف برای نظارت

برای هر `READY` بدون سؤال روتین: اجرای کامل برش و QA او، ثبت و ادامه. وابستگی‌ها با شناسه در جدول آمده‌اند؛ به‌طور پیش‌فرض شناسهٔ بعدی بعد از QA شناسهٔ جاری انجام شود. اگر مانعی قابل رفع و کم‌خطر است خودمان رفع و دوباره تست می‌کنیم. اگر وابستگی، Flutter/CI، دستگاه، تصمیم حقوقی، داده یا مجوز مستقل واقعاً ناموجود است آن گیت و برش `BLOCKED/UNKNOWN`؛ برش وابسته حق PASS و پیشروی به‌عنوان تکمیل‌شده ندارد. سپس **نزدیک‌ترین برش مستقل** انتخاب و چرخهٔ کامل مخصوص خود طی شود؛ برگشت به گیت مسدود پس از فراهم‌شدن شاهد. حدس دربارهٔ کار مالی/حقوقی یا نمایش تست اجرا‌نشده به نام PASS برای حفظ پیوستگی ممنوع. تصمیم برگشت‌پذیر درون scope را با default امن ثبت و ادامه بده؛ سؤال‌های اجتناب‌ناپذیر را دسته‌بندی کن، نه توقف نوبتی بعد هر loop.

## ۳. ECC، REA و نقش‌ها — وضعیت واقعی

**تخصیص پذیرفته‌شده برای آماده‌سازی:** همهٔ loopها P (معمار)، S (امنیت)، T (QA)، H (مستندات) و هماهنگ‌کننده دارند؛ متخصصان افزودهٔ B/W/M/D/O/R دقیقاً برای تک‌تک QF-00..QF-32 در [ماتریس نقش‌ها](PROPOSAL-SUBAGENTS-AND-CHECKPOINTS.md) مشخص‌اند و بخشی از همین برنامه‌اند. ECC انتخاب فعلی برای نقش‌هایش باقی می‌ماند، نه اینکه Superpowers/Agency بدون آزمون واقعی جایگزین شده باشند. ابزارهای جایگزین فقط پس از شاهد مدل واقعی، بررسی مجوز، حدود دسترسی و تصمیم مستند قابل پذیرش‌اند. هیچ نقشی با صرف بارگذاری متن، زیراجنت اجراشده نیست.

| نقش پیشنهادی ECC | وظیفه در هر loop | وضعیت واقعی این محیط |
|---|---|---|
| `planner` / `architect` | برش، وابستگی و قرارداد | تعریف وجود دارد؛ زیراجنت مستقل در Arena اثبات نشده |
| `tdd-guide` | بازتولید، تست شکست و regression | همان محدودیت |
| `security-reviewer` / `code-reviewer` | تهدید، رفتار، مجوز و استقلال | همان محدودیت؛ مرور عامل اصلی مستقل نیست |
| `e2e-runner` | تعامل، wiring و سناریوی سرتاسری واقعی | همان محدودیت؛ دستگاه/CI باید واقعاً قابل دسترس باشد |
| `fastapi-reviewer` / `flutter-reviewer` / `database-reviewer` | مرور پشتهٔ مرتبط در صورت وجود runtime | همان محدودیت؛ صرف فایل نقش اجرای agent نیست |
| `build-error-resolver` / `doc-updater` | رفع اشکال build و ثبت تغییر/هندآف | همان محدودیت |

در بررسی این نوبت ECC CLI checkout نسخهٔ 2.2.3 و SHA `d2ef2680594f9a17526a6e1a2e18b3d242c5d17b` دستور `consult` را واقعاً اجرا کرد و `capability:security`, `agent:code-reviewer`, `skill:security-review` را به‌صورت پیشنهاد heuristic برگرداند؛ بعضی پیشنهادهای دیگر نامرتبط بودند. این مشاوره، review یا اجرای agent نیست. گزارش نصب محلی افزونه و محدودیت restart/dependencies در [گزارش نصب ECC](../../finn/reports/ecc-native-setup.md) است. REA `6.9.0` و doctor skill سالم، ولی `environment_healthy: false`؛ REA زمانی «اجرا» است که فرمان و خروجی واقعی همان loop ثبت شود. Flutter، Dart و Docker در PATH فعلی غایب‌اند. `ecc.js --version` در checkout به install fallback رفت و خطا داد؛ نسخه از package metadata خوانده شد، نه از آن فرمان. ساعت `generatedAt` ابزار با تاریخ مرجع محلی اختلاف نشان داد؛ آن timestamp شاهد ترتیب تجاری/قانونی نیست.

## ۵. قالب شاهد مستقل برای هر QF

برای هر برش پس از آغاز اجرا در فایل گزارش جدا یا رکورد append-only (بدون overwrite گزارش موجود) ثبت کن:

```text
QF-ID / عنوان / وضعیت / زمان و branch + tree + workspace baseline
نیازمندی‌ها و وابستگی‌ها / فایل‌های تحت اثر / خطر و rollback
منشأ M/C/R/N/A: URL و نسخه و مسیر و license/notice/hash؛ A واقعی یا NONE
Forge: بازتولید/تست قرمز و نتیجه؛ diff و دلیل طراحی
Inspect: REA command و خروجی یا N/A، ECC اجرای واقعی + شناسه یا مرور دستی، یافته‌ها
QA-QF-ID: Q0..Q10 جدا؛ برای هر کدام PASS/FAIL/BLOCKED/UNKNOWN/N/A با شاهد
ماتریس action/output: role + سطح + شناسه + input + مسیر UI/API/DB + نتیجهٔ مشاهده‌شده
فرمان‌ها: cwd + دستور + exit + pass/fail/skip + بازه + محیط؛ CI run/job/link + tree
امنیت/حریم/بار: fixture، سناریوها، metrics، findings، عیب‌های باز و owner
regression و اثر بر loopهای دیگر؛ refactor/dead code و شاهد عدم مصرف
Checkpoint: محدودهٔ staged بازبینی‌شده، commit و لینک GitHub، تأیید SHA سر شاخه؛
            نتیجهٔ CI همان SHA یا UNKNOWN، مدارک محرمانه و محل امن مجاز آنها بدون مقدار
Next: مانع، loop مستقل بعدی پس از checkpoint، زمانی که باید گیت قبلی بازاجرا شود
```

اگر در حین اجرا تغییر تازه‌ای مستندات معماری، API یا مجوز را تحت تأثیر بگذارد، فایل مرتبط در همان برش به‌روزرسانی و `python3 scripts/docs_gate.py` اجرا شود. `docs_gate.py` جای بررسی کامل همهٔ لینک‌های سند تازه یا گیت کیفیت نرم‌افزار را نمی‌گیرد. برای CI/دستگاه، شناسهٔ run و revision اهمیت دارد؛ `skipped`, «مجهول»، و upstream failures شفاف بمانند. کیفیت بالا هدف قابل اندازه‌گیری و بازبینی است، نه وعدهٔ بی‌نقصی یا صفر crash در همهٔ شرایط واقعی.
