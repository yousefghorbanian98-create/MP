# PRD — Muscle Paradise (سند نیازمندی‌های محصول)

> نسخه: ۱.۰ | تاریخ: 2026-11-14 | وضعیت: پذیرفته | چرخه: M01
> ورودی: `16_LAYER_PRODUCTION_PLAN.md` لایهٔ ۱ | خروجی: همین سند + `user-stories/`
> قاعدهٔ طلایی: هیچ نیازمندی مبهمی بدون زنجیرهٔ «ورودی → موتور → خروجی → تأیید» پذیرفته نمی‌شود.

---

## ۱. خلاصهٔ اجرایی

Muscle Paradise یک «سیستم‌عامل باشگاه» local-first برای مربی شخصی و باشگاه است. هستهٔ تمایز محصول، **موتور ارزیابی ۱۴ دامنهٔ آمادگی سلامت-عملکردی** و **برنامه‌ریزی قطعی (rule-based)** است — نه یک برنامهٔ تمرینی کلیشه‌ای. دو پوستهٔ کاربری (MP Studio برای مربی/مدیر، MP Client برای عضو/کیوسک) روی یک بک‌اند مشترک FastAPI.

## ۲. اهداف و چشم‌انداز

| هدف | معیار |
|-----|--------|
| کاهش زمان صدور برنامه | از ساعت‌ها → زیر ۱۰ دقیقه (با تأیید مربی) |
| تجربهٔ ورود بدون اصطکاک | گیت چهره < ۲ ثانیه (SLO ۹۹٪) |
| اعتماد مشتری | دادهٔ بیومتریک رمزنگاری‌شده + رضایت صریح + حق حذف |
| درآمد پایدار | اشتراک/پرداخت/آفر یکپارچه + یادآوری تمدید خودکار |

## ۵. زنجیره‌های عملیاتی مفاهیم (ضد ابهام)

| مفهوم مبهم | زنجیرهٔ عملیاتی (ورودی → موتور → خروجی → تأیید) |
|------------|-----------------------------------------------|
| «شخصی‌سازی خوب برنامه» | ورودی: ارزیابی ۱۴ دامنه + هدف + آسیب/محدودیت → موتور: قواعد قطعی (ACSM/NSCA: انتخاب حرکت، حجم، شدت، پیشرفت) → خروجی: WorkoutProgram هفتگی با بار/ست/تکرار → تأیید: مربی (ویرایش/تأیید/رد با دلیل) |
| «هوشمندی تغذیه» | ورودی: مشخصات بدنی + هدف + ترجیح غذایی → موتور: قواعد کالری/ماکرو (بدن‌سازی/سلامت) → خروجی: NutritionPlan + MealItem → تأیید: مربی |
| «ورود سریع باشگاه» | ورودی: تصویر زندهٔ دوربین گیت → موتور: تشخیص چهره (YuNet/SFace) + liveness → خروجی: CheckIn ثبت‌شده در < ۲s → تأیید: در صورت شک، پذیرش (fallback QR) |
| «یادآوری هوشمند» | ورودی: رویداد (اتمام اشتراک، غیبت ۷ روزه، بازآزمایی ۶–۸ هفته) → موتور: APScheduler + قالب پیام → خروجی: اعلان درون‌برنامه‌ای/پیامک → تأیید: نرخ تعامل در گزارش مدیر |
| «گزارش مدیریتی» | ورودی: رویدادهای مالی/حضور → موتور: تجمیع KPI → خروجی: داشبورد + گزارش هفتگی → تأیید: مدیر |

## ۷. معیارهای پذیرش (Given/When/Then) — نمونه‌های کلیدی (کامل در `user-stories/`)

**US-101 ورود OTP**
- **Given** عضو با شمارهٔ موبایل معتبر در سامانه
- **When** شماره را وارد می‌کند و OTP ارسال/تأیید می‌شود
- **Then** JWT access/refresh صادر می‌شود؛ OTP فقط هش‌شده ذخیره شده؛ ۵ بار اشتباه = قفل موقت + rate-limit

**US-203 تأیید برنامه توسط مربی**
- **Given** ارزیابی ۱۴ دامنه کامل + هدف عضو
- **When** مربی «ساخت برنامه» را می‌زند و خروجی موتور قواعد را بررسی می‌کند
- **Then** برنامه با وضعیت `pending_coach` ساخته می‌شود؛ بدون تأیید مربی برای عضو قابل مشاهده نیست؛ هر تغییر مربی در audit log ثبت می‌شود

**US-106 چک‌این چهره**
- **Given** عضو رضایت بیومتریک داده و FaceTemplate رمزنگاری‌شده ثبت شده
- **When** جلوی دوربین گیت می‌ایستد
- **Then** در < ۲ ثانیه (SLO ۹۹٪) شناسایی + liveness تأیید + CheckIn ثبت می‌شود؛ در صورت شک → fallback به QR/پذیرش

**US-108 مالکیت دادهٔ بیومتریک**
- **Given** عضو دارای FaceTemplate
- **When** «حذف چهره» را تأیید می‌کند
- **Then** embedding رمزنگاری‌شده حذف می‌شود؛ audit log با شناسهٔ کاربر و timestamp ثبت می‌شود؛ امکان بازیابی وجود ندارد

**US-403 گزارش مالی**
- **Given** پرداخت‌های ثبت‌شده
- **When** مدیر بازهٔ زمانی را انتخاب می‌کند
- **Then** مجموع درآمد، تعداد تراکنش، بدهکاران و خروجی CSV تولید می‌شود؛ اعداد فقط از دیتابیس (نه LLM)

## ۸. نیازمندی‌های غیرعملکردی (NFR)

| شناسه | نیازمندی | معیار |
|-------|----------|-------|
| NFR-1 | کارایی گیت ورود | ۹۹٪ پاسخ‌ها < ۲ ثانیه (k6) |
| NFR-2 | RTL و فارسی | تمام UI فارسی RTL + Vazirmatn + تقویم جلالی + ریال |
| NFR-3 | حریم خصوصی | FaceTemplate فقط embedding رمزنگاری‌شده (PyNaCl)؛ رضایت صریح؛ حق حذف |
| NFR-4 | امنیت | OTP/رمز فقط هش‌شده؛ JWT با ابطال refresh؛ RBAC چهار نقش؛ audit log |
| NFR-5 | آفلاین | برنامهٔ امروز در Client با drift کش می‌شود |
| NFR-6 | در دسترسپذیری | بدون Ollama هم سیستم کار می‌کند (LLM فقط توضیح) |
| NFR-7 | بازتولیدپذیری | migration از صفر؛ استک با یک دستور؛ نصب ECC پین‌شده |
| NFR-8 | G8 | هیچ عدد بار/ست/تکراری از LLM نمی‌آید — فقط موتور قواعد |
