# گزارش پیش از اجرا — فیش کارت‌به‌کارت، تلگرام، بله و n8n

تاریخ: 2026-11-18. وضعیت: **فقط پژوهش و پیشنهاد؛ هیچ اتصال، workflow، secret، API یا تغییر مالی اجرا نشده است**. برنامهٔ قبلی و وضعیت پیاده‌سازی در [طرح M113](PLAN-MANUAL-TRANSFER.md) و [گزارش شواهد REA](../../finn/reports/rea/m113-review.md) هستند. در workspace قبلی فقط policy مستقل و تست آن وجود دارد و مسیر کارت‌به‌کارت عملیاتی نیست.

## نتیجهٔ جست‌وجو

- تلگرام: [قالب n8n شمارهٔ 5074](https://n8n.io/workflows/5074-ai-sales-agent-with-telegram-approvals-and-google-sheets-sync/) طبق توضیح نویسنده ربات فروش، اسکرین‌شات پرداخت و تأیید انسانی دارد. برای رستوران و وابسته به Gemini و Google Sheets است؛ در MP اجرا یا ممیزی نشده و اثبات تطبیق بانکی، امنیت یا سازگاری با ledger MP نیست. صفحه «Use for free» می‌گوید، نه اینکه همهٔ سرویس‌های جانبی رایگان‌اند یا مجوز توزیع کد الگو بررسی شده است.
- [قالب شمارهٔ 22542](https://n8n.io/workflows/22542-file-employee-expenses-from-telegram-receipts-with-openai-and-xero/) فیش را از تلگرام می‌گیرد و تأیید و ثبت هزینهٔ کارکنان را توصیف می‌کند؛ OpenAI، Google Sheets و Xero می‌خواهد و مربوط به تسویهٔ کارت‌به‌کارت مشتری نیست. بررسی فقط در سطح توضیح صفحه بوده است.
- [قالب شمارهٔ 828](https://n8n.io/workflows/828-send-the-astronomy-picture-of-the-day-daily-to-a-telegram-channel/) مثال ارسال تصویر به تلگرام است، نه فیش. [مستندات رسمی node تلگرام](https://docs.n8n.io/integrations/builtin/app-nodes/n8n-nodes-base.telegram/message-operations) ارسال تصویر binary را پشتیبانی می‌کند. یک template کاملِ بررسی‌شده و منطبق بر MP برای ارسال فیش به هر دو پیام‌رسان پیدا نشد؛ این نبودِ نتیجه در جست‌وجوی حاضر است، نه اثبات نبود در کل کاتالوگ.
- بله: [مستندات رسمی API](https://docs.bale.ai/) ارسال تصویر با `sendPhoto` و بارگذاری `multipart/form-data` را توصیف می‌کند. در جست‌وجوی کاتالوگ رسمی n8n template مشخص و قابل‌تأیید مخصوص فیش بله پیدا نشد. نمونهٔ [community node](https://github.com/mtp1376/n8n-nodes-bale-messenger) موجود است؛ metadata npm نسخهٔ `0.2.11` را MIT و تاریخ آخرین تغییر بسته را 2024-04-20 گزارش کرد. این **node است نه workflow آماده**؛ نصب یا تست یا audit امنیتی نشده است. همچنین نباید فرض کرد API بله دقیقاً معادل تلگرام است؛ جدول رسمی `sendPhoto` در زمان بررسی `from_chat_id` را الزامی فهرست می‌کند و رفتار واقعی و payload باید با تست و در صورت نیاز پشتیبانی بله روشن شود.
- n8n Community برای استفادهٔ واجد شرایط خودمیزبان حق استفادهٔ رایگان دارد ولی [Sustainable Use License](https://docs.n8n.io/n8n-community-license/community-license/license-faq) از نوع fair-code و نه متن‌باز OSI است؛ سرور/نگهداری هزینه دارد. ارائه به چند باشگاه، credentialهای مشتری و بسته‌بندی مجدد قبل از انتشار نیازمند بررسی سناریوی واقعی و در صورت ابهام تأیید n8n است. مجوز خود templateها جداگانه باید پیش از کپی بررسی شود.

## معماری پیشنهادی

1. عضو داخل MP سفارش یا درخواست شارژ ایجاد می‌کند؛ مبلغ صحیح ریالی و مقصد معتبر در سرور snapshot می‌شوند. عضو پس از واریز خارج از برنامه، فیش را **داخل MP** ارسال می‌کند. فیش در storage خصوصی اعتبارسنجی و ثبت می‌شود؛ پرداخت هنوز pending است.
2. MP بعد از ثبت پایدار درخواست، event در outbox همان تراکنش ثبت می‌کند. کانال پیام‌رسان **اختیاری و پیش‌فرض خاموش** است. مسیر پیشنهادی کم‌افشاتر: اطلاع‌رسانی فقط با شناسهٔ opaque و لینک نیازمند ورود به Studio، بدون خود تصویر. ارسال کپی تصویر به تلگرام/بله، در صورت تصمیم مالک و اطلاع‌رسانی شفاف به عضو، حالت جداگانه و opt-in است؛ کنترل نسخه‌های طرف پیام‌رسان کامل نیست.
3. اگر n8n انتخاب شود، فقط انتقال و اعلان را انجام می‌دهد: event تأییدشده، retrieval سروربه‌سرور محدود و موقت از فایل خصوصی، node تلگرام برای ارسال binary؛ برای بله HTTP Request با multipart و بررسی پاسخ `ok` و API مستند. فایل روی URL عمومی قرار نمی‌گیرد. جایگزین کم‌وابستگی: worker بومی MP با adapter برای هر API و بدون n8n؛ از منظر مجوز و عملیات ساده‌تر، ولی باید طراحی و تست شود.
4. تصمیم در Studio و فقط توسط کارشناس مجاز انجام شود، پس از بررسی مستقل گردش بانک، مبلغ و حساب مقصد. API سرور با قفل/قیود و idempotency، تصمیم و تغییر ledger/سفارش را اتمی می‌کند. پیام‌رسان و n8n حق تأیید یا ثبت پول ندارند. دکمهٔ پیام فقط می‌تواند به Studio نیازمند احراز هویت هدایت کند.
5. اگر منظور ارسال مستقیم فیش توسط عضو به ربات پیام‌رسان است، این یک مسیر جایگزین با مسئلهٔ انتساب امن حساب MP به هویت ربات، محدودیت فایل، پشتیبانی و بازیابی است؛ فقط با اتصال امن یک‌بارمصرف و کنترل مالکیت و تست جداگانه قابل طراحی است. راه پیشنهادی فاز اول، آپلود در خود اپ و اعلان برای کارشناس است، نه وابسته‌کردن عضو به نصب پیام‌رسان.

## ریسک‌ها، چاره و گیت‌ها

| ریسک | راهکار پیشنهادی | گیت قبل از فعال‌سازی |
|---|---|---|
| commit داخلی checkout و نیمه‌ثبت | بازآرایی مرز transaction پرداخت/سفارش/موجودی بدون تغییر رفتار روش `card` حضوری؛ rollback و idempotency | failure injection، تست روش‌های قدیمی، رقابت روی PostgreSQL واقعی در CI |
| جعل یا تکرار فیش، مبلغ اشتباه | تأیید انسانی در برابر گردش بانک، تطبیق مبلغ/مقصد/مرجع معتبر؛ وضعیت مغایرت و رسیدگی دستی؛ OCR تأیید نیست | تست بازپخش مرجع، تفاوت مبلغ، رد/ارسال مجدد و حساب اشتباه |
| مسابقهٔ تأیید/لغو/انقضا | قفل یا CAS و constraint دیتابیس؛ انتشار پرداخت و stock restore فقط یک‌بار؛ فیش در حال بررسی خودکار منقضی نشود | دو کارشناس و retry همزمان روی PostgreSQL؛ reconciliation ledger و stock |
| افشای فیش و اطلاعات بانکی | private storage، role/branch/owner، کنترل محتوا/decode، محدودیت بایت/پیکسل، rate-limit، عدم ثبت فایل/توکن در لاگ؛ حذف و retention مصوب | IDOR، جعل MIME، فایل خراب/بزرگ/متحرک، لاگ و تست پاک‌سازی؛ سیاست نگهداری/بکاپ/حذف تعیین شود |
| ارسال به چت اشتباه | مقصد ثابت متعلق به هر شعبه از تنظیمات مالک؛ تست با فیش ساختگی؛ جلوگیری از آدرس مقصد انتخابی عضو؛ chat خصوصی و محدود | تست isolation شعبه، توکن نامعتبر، تغییر گیرنده و بازبینی دسترسی اپراتورها |
| قطعی، timeout و ارسال تکراری | outbox پایدار، retry با backoff، هشدار و dead-letter و امکان ارسال مجدد از Studio؛ شبکه در تراکنش DB نباشد | تست قطع شبکه و crash؛ عدم ارسال لزوماً مانع دیدن فیش در Studio نیست. timeout بعد از پذیرش پیام ممکن است ارسال تکراری بسازد؛ exactly-once در پیام‌رسان تضمین نمی‌شود، تکرار مالی به backend محدود است |
| نشت از n8n، webhook و provider | service identity محدود، TLS، endpoint داخلی یا webhook دارای احراز و ضد replay، حداقل payload؛ عدم ذخیرهٔ دادهٔ حساس اجراهای موفق/خطا/دستی تا حد امکان؛ retention و پاک‌سازی جدا برای binary، backup و اجرای منتظر؛ token در secret store و redaction مسیر URL | تست replay، auth، لاگ و failure؛ هیچ تضمینی بر حذف کامل نسخهٔ پیام‌رسان یا اسکرین‌شات کاربران وجود ندارد. [تنظیم ذخیرهٔ اجرا](https://docs.n8n.io/deploy/host-n8n/configure-n8n/scaling/manage-execution-data) محدودیت pruning حالت waiting/annotated را بیان می‌کند |
| ناسازگاری/اختلال شبکهٔ تلگرام یا بله | adapter مستقل و feature flag برای هر کانال؛ آزمون از محل deployment واقعی و امکان تغییر/غیرفعال‌سازی؛ Studio مرجع اصلی | تست زنده با دادهٔ ساختگی و ربات آزمایشی در همان شبکه؛ موفقیت محلی تضمین دسترسی عملیاتی نیست |
| مانع مجوز، هزینه و supply chain | استفاده از API استاندارد یا node داخلی؛ اگر community node یا template کپی می‌شود، audit، pin و مجوز جداگانه؛ n8n را الزامی نکنیم | تأیید سناریوی تجاری/بسته‌بندی و هزینهٔ واقعی پیش از استقرار |
| تأخیر در عملیات و تسویه | SLA مشخص، صف بررسی و یادآوری، وضعیت قابل‌مشاهده و پشتیبانی برای اختلاف | آزمون قطع پیام‌رسان، اپراتور غایب و مدیریت مغایرت |
| کلید امضا، رازهای تاریخی، انتشار | چرخش واقعی secrets و هماهنگی حذف history/refs و اعتبارسنجی CI؛ کلید Android خارج از چت، سپس build امضاشده | secret scan، CI کامل، ساخت امضاشده و تست دستگاه؛ این‌ها از M113 مستقل‌اند |
| اختلاف شاخهٔ remote/local و workspace قبلی | بررسی commitها و patchهای موجود، تهیهٔ نسخهٔ امن و reconciliaton بدون pull/reset/force یا overwrite | diff و تست روی نتیجهٔ نهایی، سپس push عادی همین شاخه؛ تا آن زمان وضعیت GitHub از workspace عقب است |
| محدودیت REA/ECC/Repowise | گزارش نقصان، بازبینی کد و گیت‌های مستقل؛ Mermaid نسخه‌شده تا در دسترس شدن ابزار | هیچ ادعای refresh واقعی index یا اجرای subagent مستقل بدون شاهد |

## ترتیب پیشنهادی بعد از تأیید

1. آزمایش طراحی آفلاین و migration افزایشی و بررسی مرز تراکنش checkout؛ سپس API درخواست/وضعیت و storage خصوصی، خاموش به‌صورت پیش‌فرض.
2. بررسی انسانی و تطبیق/ledger، idempotency، همزمانی PostgreSQL و failure injection؛ سپس Flutter و Studio و سناریوهای E2E.
3. اعلان اختیاری بدون تصویر؛ سپس در صورت تأیید سیاست، ارسال تصویر از طریق worker داخلی یا n8n، ابتدا تلگرام و بله هرکدام با تست مستقل دادهٔ ساختگی.
4. مستندات، تست CI و device، تست شبکه و دسترسی واقعی، reconciliaton شاخه، و rollout محدود با مانیتورینگ و راه بازگشت.

پیش‌فرض پیشنهادی: کارت‌به‌کارت به‌عنوان روش مستقل، پرداخت و درگاه فعلی حفظ می‌شوند؛ هیچ تصمیم مالی از پیام‌رسان صادر نمی‌شود. مقادیر دقیق retention، شماره/مالک کارت، اختیار نقش‌ها، opt-in ارسال تصویر و راه استقرار باید قبل از فعال‌سازی واقعی نهایی شوند، نه لزوماً پیش از کدنویسی خاموش.
