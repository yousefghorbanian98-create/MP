# گزارش اجرای آزمایشی ECC، REA و QA ساختگی

**نتیجهٔ گیت شروع: `BLOCKED`.** آزمایش واقعی میزبان و ابزارها انجام شد، اما زیراجنت مستقل و QA مستقل اجرا نشدند؛ در این میزبان احراز هویت ارائه‌دهنده وجود نداشت. این نتیجه صرفاً وضعیت همین نشست است و تجربه یا امکان اجرای ECC در نشست‌های دیگر را نفی نمی‌کند. QF-00 و توسعهٔ محصول آغاز نشده‌اند.

## دامنه و حفاظت

- در آغاز: شاخه `arena/b0e55b62-mp` و HEAD و remote هر دو `be9e40e77f31f3b277fa1ce1d34b899d510acf81`، ۴۶ مسیر dirty/untracked و صفر staged؛ آثار قبلی دست‌نخورده ماندند.
- همهٔ آزمایش‌ها با محتوای ساختگی، cwd و HOME موقت و بدون کد MP، دادهٔ واقعی، credential، تنظیم MCP پروژه، hook یا تغییر محصول بودند. فقط metadata محدود از `auth status` میزبان جاری خوانده شد؛ هیچ مقدار ورود یا کلیدی در خروجی یا گزارش ثبت نشده است. sandbox برای تماس خروجی به میزبان‌های محدودی دسترسی دارد؛ دسترسی به شبکهٔ ارائه‌دهندهٔ مدل در این آزمایش اثبات نشده است.
- نسخهٔ واقعی REA `6.9.0`، ECC `ecc-universal 2.2.3` و commit پین‌شدهٔ ECC `d2ef2680594f9a17526a6e1a2e18b3d242c5d17b`. نسخهٔ واقعی میزبان آزمایشی Claude Code `2.1.328` در محیط موقت از npm بدون lifecycle scripts تهیه و binary اختصاصی Linux اجرا شد؛ این نصب، ابزار delegation به Arena اضافه نمی‌کند.

## آزمون واقعی parent/child

1. روی میزبان فعلی و HOME ایزوله، `claude auth status --json` به‌ترتیب exit 1 و metadata `loggedIn=false`, `authMethod=none` گزارش کرد. در محیط فرآیند نیز متغیرهای متداول کلید مدل بررسی شدند و مقدار تنظیم‌شده‌ای دیده نشد؛ صرف این نتیجه برای سایر نشست‌ها یا روش‌های احراز هویت حکم نیست.
2. دو تعریف موقت `ecc-planner-smoke` و `ecc-security-smoke` با متن نقش‌های عمومی ECC از مسیر `agents/` و بدون ابزار کودک ساخته شدند؛ این‌ها **نقش‌های دستی** بودند، نه اثبات فعال‌بودن افزونهٔ `ecc@ecc`. درخواست والد فقط یک تابع ساختگی و درخواست دو child برای plan و security review داشت. `--tools Task`, `--strict-mcp-config`, `--no-session-persistence`, `--disable-slash-commands`, `--permission-mode plan` و `--setting-sources ''` استفاده شدند؛ بدون bypass-permissions، allowlist سراسری یا دادهٔ MP.
3. فرآیند میزبان exit 1 داد. در پیام init ابزار `Task` و هر دو نام نقش دیده شدند؛ result دارای `is_error=true` و دستهٔ خطای احراز هویت/API بود. هرچند subtype خروجی `success` نام داشت، exit و `is_error` شکست را نشان می‌دهند. **صفر tool-use از نوع Task/Agent و صفر پیام child با parent ID** مشاهده شد؛ بنابراین نه planner، نه security-reviewer و نه QA مستقل واقعاً اجرا شدند.
4. سقف `--max-budget-usd 0.01` یک حد محافظتی CLI بود، نه تأیید خرید یا ادعای مصرف. محیط child هیچ credential نداشت و model call یا هزینه‌ای مشاهده نشد. دسترسی provider یا کارکرد سیستم با حساب واردشده آزموده نشد.

## آزمون‌های آفلاین واقعی، ولی نه QA مستقل

- REA `inspect-api-contract` روی `finn/fixtures/ecc-qa-smoke/contract.json` ساختگی و دو عملیات inline اجرا شد: exit 0، ۲ operation slot و ۲ مورد declared، صفر unknown در آن بخش. `complete-within-scope` فقط پوشش همان مسیرهای inline را بیان می‌کند؛ REA در این خروجی reference، schema validation و security contract را بررسی نکرده است. `rea doctor` با HOME موقت exit 1 و `healthy=false` بود؛ موفقیت این تست محدود به معنی آماده‌بودن همهٔ providerهای REA نیست.
- ECC `consult` روی درخواست ساختگی مربوط به امنیت و QA اجرا شد و exit 0 با ۶ توصیه داد. این خروجی heuristic است، نه اجرای مدل یا زیراجنت.
- harness تست استاندارد Python روی fixture ساختگی اجرا شد: `unsafe_policy` عمداً exit 1 با ۴ تست و ۳ شکست داشت؛ `safe_fixture` exit 0 با ۴ تست موفق داشت. آزمون‌ها نقش عضو، ادمین بدون اجازه، فقدان تطبیق مستقل و تأیید/تکرار صوری را پوشش می‌دهند. این مقایسه توسط عامل اصلی و بدون agent مستقل انجام شد؛ `safe_fixture` به بانک، تراکنش DB یا محصول متصل نیست و الگوی production نیست.
- اجرای نخست unittest به‌اشتباه از cwd والد انجام شد و هر دو variant با خطای import شکست خوردند. پس از اصلاح cwd، دو نتیجهٔ بالا به‌دست آمدند و دوباره از مسیر fixture قابل‌انتقال تکرار شدند. هر دو رخداد ثبت شده‌اند؛ شکست اولیه PASS محسوب نمی‌شود.
- فایل‌های قابل‌بازتولید [fixture و دستور اجرا](../../finn/fixtures/ecc-qa-smoke/README.md) هستند. ابزارها و خروجی خام در `/tmp` موقت ماندند و در مخزن منتشر نشدند. fixture عمداً ناامن است و فقط برای آزمون به کار می‌رود.

## وضعیت و گام بعد

| گیت | نتیجه |
|---|---|
| REA روی OpenAPI ساختگی | `PASS` فقط برای اجرای محدود فوق، نه audit |
| ECC consult | `PASS` فقط اجرای heuristic، نه زیراجنت |
| harness ساختگی ناامن/مقایسه‌ای | خروجی مورد انتظار، نه QA محصول |
| parent → child واقعی ECC planner | `BLOCKED`؛ هیچ child ثبت نشد |
| child مستقل security/QA | `BLOCKED`؛ هیچ child یا بازبینی مستقل ثبت نشد |
| QF-00 و میکرولوپ‌های محصول | `NOT RUN` |

برای رفع مانع، اجرای همین آزمایش در **یک میزبان پشتیبانی‌شده با دسترسی مجاز به مدل و شبکه و حدود هزینهٔ مشخص**، یا استفاده از ابزار delegation واقعی Arena در صورت فراهم‌شدن آن لازم است؛ بدون فرستادن رمز یا token در چت. باید شاهد tool-call و شناسه/trace والد و هر دو child، خروجی جداگانه و دریافت آن توسط والد ثبت شود. پس از آن هم باید استقلال بازبینی QA و دسترسی‌های آن را برای هر loop ارزیابی کرد. ارسال کد MP به سرویس مدل بیرونی، خرید، cloud، release و دادهٔ واقعی همچنان بدون اجازهٔ مربوط انجام نمی‌شود.
