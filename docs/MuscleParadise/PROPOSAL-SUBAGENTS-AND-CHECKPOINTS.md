# پیشنهاد تخصیص زیراجنت‌ها و ثبت پایدار هر میکرولوپ

**وضعیت:** `APPROVED FOR PREPARATION / تخصیص نقش‌ها با واگذاری تصمیم به عامل پذیرفته شد`؛ نه مدرک اجرای agent است، نه آغاز توسعه. ثبت checkpoint GitHub در [چرخهٔ QF، بند ۲.۱](PLAN-FINN-ECC-MICROLOOPS-QA.md) الزامی است. ECC انتخاب فعلی است؛ جایگزینی با Superpowers/Agency بدون آزمون واقعی و ارزیابی نهایی تصویب نشده است؛ [گزارش مقایسه](REPORT-FREE-ECC-ALTERNATIVES-2026-11-18.md).

## ۱. ساختار کار برای هر میکرولوپ

**هماهنگ‌کنندهٔ اصلی** دامنه، وابستگی‌ها، محدودیت‌ها و حفاظت workspace را کنترل می‌کند، وظایف را تخصیص می‌دهد، نتایج و diff را بررسی می‌کند، گیت‌ها را اجرا و ثبت می‌کند و تنها او مسئول checkpoint است. نقش زیر را فقط زمانی «زیراجنت» بنام که میزبان واقعی آن را به فرایند/نشست child مستقل با شاهد parent/child اجرا کند. اگر میزبان، مجوز استفاده از مدل یا توان لازم وجود ندارد، آن اجرا `BLOCKED` و کار دستی صریحاً غیرمستقل ثبت می‌شود؛ از اجرای شبیه‌سازی‌شده یا خواندن متن نقش به نام زیراجنت واقعی استفاده نشود.

| کد نقش پیشنهادی | وظیفهٔ مشخص | حدود اختیار |
|---|---|---|
| **P — برنامه‌ریز/معمار** | برش، شرایط پذیرش، وابستگی و طرح API/DB/UI؛ ثبت تهدید و مسیر رگرسیون. | ترجیحاً فقط‌خواندنی؛ طراحی او مجوز تغییر مستقل نیست. |
| **B — بک‌اند/API** | FastAPI، قانون کسب‌وکار، احراز هویت/مجوز، تراکنش و خطاهای سروری در همان برش. | فقط فایل‌های واگذارشده؛ بدون Git/history، secret و دادهٔ واقعی. |
| **W — وب کادر** | React/Studio، فرم‌ها، دسترسی‌پذیری، اتصال واقعی به API و حالات loading/error. | فقط محدودهٔ تعیین‌شده؛ تغییر منو به‌تنهایی enforce سروری نیست. |
| **M — Android/Flutter** | رابط عضو، state، شبکه، UX، QR و اعلان برای برش مربوط. | بدون تغییر تنظیمات امضای واقعی؛ CI و device فقط اگر موجود/مجازند. |
| **D — داده/DB** | schema و migration، سازگاری، تراکنش، ایندکس، race و rollback روی fixture. | فقط DB آزمایشی؛ تغییر دادهٔ واقعی ممنوع. |
| **S — امنیت و حریم** | threat model، authorization/IDOR، audit/redaction، دادهٔ حساس، وابستگی و secrets scan امن؛ یافته‌ها با severity و شاهد. | بررسی مستقل و ترجیحاً فقط‌خواندنی؛ به secret یا history دستکاری‌شده نیاز ندارد. |
| **T — QA و اتصال** | جدول action/output، تست منفی و واقعی UI→API→DB، تست حوزه، رگرسیون و ثبت Q0–Q10؛ در موارد نیاز load/crash/device. | reviewer جدا از implementer در صورت دسترسی؛ تست اجرا‌نشده PASS نیست. |
| **O — زیرساخت/CI/عملیات** | workflow، شبکه، worker، backup/restore، مشاهده‌پذیری، Android build و سنجش خطا/بار در محیط مجاز. | بدون deploy، خرید، release، تغییر secret و استقرار واقعی بدون اجازهٔ جدا. |
| **R — تحقیق/منشأ** | REA واقعی در صورت نیاز و دسترسی، بررسی کد/مجوز/نسخهٔ dependency، رد یا پیشنهاد نامزد و ثبت منبع. | نتیجه partial را audit کامل ننامد؛ بدون ارسال کد/داده به سرویس بیرونی بدون مجوز. |
| **H — مستندات و انتقال** | به‌روزرسانی API/معماری/ماتریس action، صورت‌جلسهٔ QA و handoff؛ تأیید links و notice. | بر اساس شواهد واقعی؛ هیچ push، commit یا تصمیم انتشار بدون هماهنگ‌کننده. |

این کدها **نام وظیفه** هستند نه ادعای اینکه هر عنوان در ECC، Agency یا میزبان انتخاب‌شده عیناً وجود دارد. می‌توان آن‌ها را به نقش‌های واقعی همان میزبان مانند `planner`, `security-reviewer`, `API Tester` یا `Mobile App Builder` پس از بررسی تطبیق داد. نقش‌های متفاوت الزاماً مدل‌های متفاوت نیستند و فراخوانی هر کدام ممکن است هزینه/محدودیت مدل داشته باشد. کاربر پیش‌تر از زیراجنت در نشست دیگری استفاده کرده است؛ وجود یا فقدان امکانات همان نشست را از آزمایش این sandbox نتیجه‌گیری نکن.

### توالی اجباری هر QF

1. هماهنگ‌کننده + **P**: baseline، محدوده و پذیرش؛ **R** فقط اگر بررسی منبع یا REA برای آن برش لازم است.
2. یک implementer اصلی با ترکیب مناسب **B/W/M/D/O**، با تست شکست یا دلیل مستند، سپس اتصال کامل و رفع اشکال. اگر دو agent روی بخشی همکاری دارند، محدوده‌های نوشتن غیرهمپوشان یا اجرای سری؛ هیچ agent بدون هماهنگی در یک فایل مشترک نمی‌نویسد.
3. **S** بررسی امنیت/حریم و **T** QA مستقل همان loop شامل Q0–Q10 و تست interaction، wiring، رگرسیون، بار/crash در موارد مربوط. استقلال فقط با reviewer واقعی و جداگانه قابل ادعاست. اگر مستقل در دسترس نیست، بازبینی دستی شفاف + گیت استقلال `BLOCKED`؛ به معنی PASS کامل نیست.
4. **H** مستندات و handoff مبتنی بر شواهد را تنظیم می‌کند؛ هماهنگ‌کننده نتایج، diff، provenance، ریسک و redaction را بررسی و طبق بند ۲.۱ برنامهٔ QF checkpoint امن commit/push/verification را انجام می‌دهد. سپس حلقهٔ بعدیِ مجاز آغاز می‌شود.
5. روال از پیش تأییدشده بدون سؤال نظارتی تکراری ادامه می‌یابد؛ مانع وابسته ثبت می‌شود. **اگر checkpoint امن در GitHub امکان‌پذیر نباشد، شروع توسعهٔ loop بعدی متوقف است** تا خروجی صرفاً محلی جمع نشود؛ اقدامات غیرمخرب برای رفع همان مانع ادامه می‌یابند.

## ۲. نقش‌ها و تحویل هر یک از ۳۳ میکرولوپ

در **همهٔ** ردیف‌ها P، S، T و H نقش پایهٔ بالا را دارند و هماهنگ‌کننده مسئول تأیید و checkpoint است؛ ستون دوم نقش اجرایی/تخصصی افزوده را نشان می‌دهد، نه جایگزین این کنترل‌ها. هدف و وابستگی و Q0–Q10 دقیق در [برنامهٔ اصلی](PLAN-FINN-ECC-MICROLOOPS-QA.md) باقی است.

| 00 | فهرست همهٔ قابلیت‌ها | **R + B + W + M + D + O:** فهرست فایل، API، DB، صفحه و تمام action/output؛ مالک هر مورد، تغییرات local و خطر secret فقط با metadata. |

## ۳. ثبت GitHub و موارد باقی‌مانده از قبل

مالک می‌خواهد پس از هر میکرولوپ هیچ خروجی لازم فقط در sandbox نماند. این خواسته در بند ۲.۱ برنامه ثبت شد: گزارش، کد و شواهد قابل انتشار همان برش باید پس از بازبینی، به شاخهٔ فعلی push و با SHA/remote کنترل شوند؛ CI و گیت‌های کیفی جدا هستند. GitHub این repository عمومی است؛ secret، کلید، credential، دادهٔ شخصی، فایل امضا و binary/cache نباید در آن منتشر شوند. ابزارهای موقت با دستور و نسخه مستند می‌شوند؛ برای هر محتوای لازم اما حساس باید محل خصوصی تأییدشده وجود داشته باشد.

**مانع فعلی قبل از شروع:** آخرین بررسی `HEAD=5482930` و `origin/arena/b0e55b62-mp=8e72de9` با ۸ commit فاصله، و ۶۴ تغییر dirty/untracked در workspace بود؛ فاصله پیش از تغییرات همین درخواست اندازه‌گیری شد. حتی مستندات این برنامه و گزارش‌ها ممکن است untracked باشند و در clone تازه وجود نداشته باشند. قبل از هر commit/push باید فهرست محتوای لازم، تغییرات قبلی و اختلاف remote دقیق و غیرمخرب بازبینی شود؛ هیچ stage انبوه، pull/reset، تغییر branch یا force push مجاز نیست. اگر مسیر امن پیدا نشد، **شروع توسعه مسدود** و از مالک راه انتقال/پشتیبان امن خواسته شود. مجوز checkpoint به معنی مجوز عمومی‌کردن اطلاعات حساس یا merge main نیست.

## ۴. تصمیم و گام بعدی

مالک اختیار تصمیم و انجام آماده‌سازی تا لحظهٔ شروع را داده است؛ نقش‌بندی بالا برای آماده‌سازی پذیرفته شد. در همین مرحله باید میزبان و مدل واقعی و مجاز صحت‌سنجی، نقش‌ها با قیود پروژه سازگار و checkpoint امن روی همین branch بررسی شود؛ سپس با دستور شروع، QF-00 با QA و checkpoint جداگانه آغاز شود. هر زیراجنت باید با شاهد واقعی اجرا شود؛ در صورت مانع در اجرا یا checkpoint، وضعیت همان gate صادقانه ثبت و ادامهٔ مجاز تعیین شود. این اختیار به معنی مجوز خودکار برای خرید، deploy، release، ارسال کد به مدل بیرونی یا انتشار secret نیست.


## ۵. افزونهٔ تخصیص ارزش‌های تازه — بدون ادعای اجرا

برای درخواست ارزش‌های حضور/تمرین/تغذیه/چت/نقشه/OCR از همان نقش‌های توافق‌شده و QFهای موجود استفاده شود، با نگاشت و معیار اختصاصی [OV-01..11](PLAN-OSS-VALUE-MICROLOOPS-2026-11-18.md). P/S/T/H در همهٔ برش‌ها الزامی‌اند؛ R برای منشأ و حقوق، B/W/M/D/O طبق ماتریس هر ردیف. بازبین T باید واقعاً مستقل باشد؛ در نبود میزبان/مدل و QA مستقل، status=`BLOCKED` و وانمود به زیراجنت ممنوع است. checkpoint امن و CI همان SHA همچنان شرط ادامه‌اند.
