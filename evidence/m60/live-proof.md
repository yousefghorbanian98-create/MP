# اثبات زندهٔ M60 (R3 / R5 / R6) — HTTP واقعی، نه TestClient

- تاریخ: ۲۰۲۶-۱۱-۱۶
- سرور: `uvicorn app.main:create_app --factory --host 0.0.0.0 --port 8123`
- دیتابیس: `sqlite:////tmp/live_shop.db` (همان DB اثبات‌های قبلی، با دادهٔ واقعی سفارش)
- توکن‌ها با `app.security.jwt.create_access_token` از **همان کاربران واقعی DB** ساخته شدند.

هر خط زیر خروجی یک `curl` واقعی است، نه توصیف.

## R3 — نقش‌ها (لایهٔ RBAC و لایهٔ هندلر)

| درخواست | نتیجه | معنا |
|---|---|---|
| `GET /payments/finance/summary` با نقش coach | **403** | دادهٔ مالی خالص برای مربی بسته است |
| همان با نقش member | **403** | — |
| همان با نقش admin | **200** | مدیر مجاز است |
| `POST /shop/products` با نقش admin و بدنهٔ معتبر | **403** | `ensure_owner` رد می‌کند |

پیام واقعی رد شدن (برای admin، نه member):

```json
{"error":{"code":"forbidden","message":"ساخت محصول فقط با تأیید مالک سیستم (super_admin) انجام می‌شود","details":[]}}
```

**نکتهٔ مهم:** اولین تلاش من با بدنهٔ ناقص انجام شد و **422** گرفت، نه 403.
اگر آن را «تأیید» می‌گرفتم، در واقع هیچ چیز دربارهٔ مجوزها ثابت نشده بود.
بدنه دوباره با فیلدهای اجباری (`title`, `sku`, `price_rial`, `category_id`)
فرستاده شد و این‌بار 403 آمد.

## R5 — رسید سفارش و محدودهٔ دسترسی

`GET /shop/orders/2/receipt` با نقش member (صاحب سفارش) → **200**:

```json
{"receipt_no":"O-000002","member_id":3,"member_name":"عضو تست 1","status":"paid",
 "lines":[{"title":"پروتئین وی ۲ کیلوگرمی","variant":null,
           "unit_price_rial":2900000,"qty":1,"line_total_rial":2900000}],
 "items_total_rial":2900000,"total_rial":2900000,
 "payment":{"id":5,"method":"wallet","status":"paid",
            "reference_id":"wallet-0463256de4d4"},
 "branch":"Muscle Paradise"}
```

| درخواست‌کننده | نتیجه |
|---|---|
| عضو شمارهٔ ۳ (صاحب سفارش) | **200** |
| عضو شمارهٔ ۴ (عضو دیگر) | **403** — `{"code":"forbidden","message":"دسترسی فقط به دادهٔ خودتان مجاز است"}` |
| admin (کارمند) | **200** — کارمند همه را می‌بیند (طراحی) |

توجه: در اثبات اول از نقش `coach` استفاده کردم و 200 گرفتم و **نزدیک بود اشتباه
نتیجه بگیرم**. coach کارمند است، نه «عضو دیگر»؛ برای اثبات محدوده باید عضو
دیگری امتحان می‌شد. این‌جا با عضو شمارهٔ ۴ تکرار شد و 403 آمد.

## R6 — انیمیشن حرکت

`GET /library/exercises/11` → **200**:

```json
{"name_fa":"لانج","image_url":"/static/exercises/11_0.jpg","gif_url":"/static/exercises/11.gif"}
```

`GET /static/exercises/11.gif` → **200**، `content-type: image/gif`، **۳۲۸٬۳۷۰ بایت**.

یعنی مسیری که API وعده می‌دهد واقعاً سرو می‌شود — نه یک رشتهٔ خوش‌بینانه.

## G1 — تاریخچهٔ پرداخت عضو (ممیزی رقابتی ۲۰۲۶-۱۱-۱۶)

سرور: `:8124` روی همان DB. توکن‌ها از کاربران واقعی ساخته شدند.

| درخواست | نتیجه |
|---|---|
| `GET /payments` با نقش member#3 | **200** — ۲ ردیف، همه `member_id=3` |
| همان، با `?member_id=99` (تلاش برای دیدن دیگری) | **200** ولی فقط `member_id=3` — پارامتر نادیده گرفته شد |
| همان، با نقش admin | **200** — ۵ ردیف از `member_id` های ۲، ۳، ۴۱ |

خط سوم یعنی محدودسازی سمت سرور واقعی است (`service.list_payments` برای نقش
`member` شناسه را با شناسهٔ خودش بازنویسی می‌کند)، نه فقط در UI. صفحهٔ کلاینت
که روی همین مسیر ساخته شد، به این محدودسازی تکیه می‌کند.
