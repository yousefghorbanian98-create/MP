# ارزیابی REA — تحلیل ساختاری APK خودمان (۲۴ آبان ۱۴۰۵)

> روش: چارچوب مهندسی معکوس **REA** (morluto/rea — MIT، ۴۶۰٬۴۰۸ ستاره) روی آرتیفکت مجاز:
> `mp-app/client/release/app-arm64-v8a-release.apk` (نسخهٔ v0.2.0-client2 — مالکیت خود پروژه).
> طبق قانون استفادهٔ REA و اصول آکادمیک، APKهای مالکیتی رقبا دیکامپایل **نمی‌شوند**؛
> بنچمارک آن‌ها در سطح فیچر می‌ماند (COMPETITIVE-BENCHMARK-2026-11-14.md).

## ۱) ابزارها و شواهد

| ابزار REA | نتیجه | شاهد |
|---|---|---|
| `identify-flutter-build` | شناسایی کامل بیلد فلاتر + digest | `finn/reports/rea/identify-flutter-build.json` |
| `inspect-artifact` (۴۱۳ کیلوبایت Evidence) | digest + مشاهدات + کاوش‌های بعدی | `finn/reports/rea/inspect-artifact.json` |
| `extract-artifact` | فهرست امن ۳۷۶ عضو APK | `finn/reports/rea/extract-artifact.json` |
| `inspect-dart-aot` | **نمادهای snapshot حذف شده‌اند** (سخت‌شدگی) — خطا «unsupported_target» خودش یک یافتهٔ مثبت امنیتی است | `finn/reports/rea/inspect-dart-aot.json` |
| `inspect-android-package` | به jadx-mcp + Java 17 نیاز دارد (در این محیط نبود) → جایگزین: `pyaxmlparser` (pypi) برای مانیفست ادغام‌شده | `/tmp/manifest-dump.xml` |
| بررسی طرح‌های امضا (درس `docs/apk-signature.md` خود REA) | بلوک امضای **v2/v3 موجود**، v1 نیست (ساخت مدرن) — امضای پایدار `mp-release` = شرط به‌روزرسانی بدون حذف | اسکریپت ساختار ZIP/Signing Block |
| اسکن راز در سورس (قاعدهٔ G6/E12) | **هیچ کلید/رمز جاسازی‌شده‌ای یافت نشد** | grep الگوهای api_key/secret/token |

## ۲) یافته‌های بحرانی — سه نقص واقعی که فقط تحلیل ساختاری آشکار کرد

| # | یافته | چرا بحرانی بود | وضعیت |
|---|---|---|---|
| R1 | **`INTERNET` در مانیفست release نبود** (فقط در debug بود) | همهٔ فراخوانی‌های API روی دستگاه واقعی شکست می‌خورد — دقیقاً همان «کار نمی‌کند»هایی که حس می‌شد | ✅ رفع‌شده + افزوده به مانیفست اصلی |
| R2 | **سیاست cleartext برای targetSdk 36 بسته بود** (بدون networkSecurityConfig) | معماری «سرور محلی روی LAN» با HTTP اصلاً وصل نمی‌شد؛ قطعی کامل ارتباط | ✅ `network_security_config.xml` (مجوز LAN؛ مسیر HTTPS داخلی M28 مستند شد) |
| R3 | **`allowBackup` غایب = پیش‌فرض true** | خروجی adb backup می‌توانست دادهٔ محلی/توکن‌ها را بیرون بکشد — مغایر ادعای حریم خصوصی NFR-3 | ✅ `allowBackup="false"` |

**یافته‌های مثبت (سخت‌شدگی تأییدشده):** debuggable=false (پیش‌فرض) · اجزای exported حداقلی (ImagePickerFileProvider غیرقابل‌دسترس، گیرندهٔ profileinstaller با مجوز DUMP) · نمادهای Dart حذف‌شده · فقط یک ABI در هر APK (split-per-abi) · امضای v2/v3 با کلید پایدار · بدون راز جاسازی‌شده.

## ۳) اثر بر بنچمارک رقابتی

این سه نقص، نمونهٔ عینی «شکاف‌هایی» است که بنچمارک سطح فیچر هرگز نشان نمی‌دهد و داور پایان‌نامه هم می‌تواند بپرسد:
«آیا APK واقعاً روی دستگاه کار می‌کند؟» — پاسخ اکنون **با شاهد ساختاری** مستند است.
درس REA (`apk-signature.md`) پیش‌تر همان ریشهٔ «نصب پکیج شکست خورد» را حل کرده بود (ثبات امضا).

## ۴) محدودیت‌های صادقانه

- سطح کلاس/متد (جداکامپایل DEX) به jadx-mcp + Java 17 نیاز دارد که در این محیط در دسترس نبود؛
  جای آن، پارسر مستقیم مانیفست + پارس ساختار امضا به‌کار رفت (همان خروجی‌های مورد نیاز audit).
- تحلیل رانتایم (اسکرین‌شات دستگاه، trace) نیازمند دستگاه/شبیه‌ساز است — در صف Q3 (تست دوربین E2E) می‌آید.
